3. Architecture Analysis

3.1 Overall Architecture Pattern

Pattern: Multi-Tier SaaS with Multi-Tenancy

  • Presentation Tier: React SPA with component-based UI
  • API Tier: RESTful endpoints with JWT authentication
  • Service Tier: Business logic with Spring Services
  • Data Tier: PostgreSQL with JPA/Hibernate ORM

3.2 Multi-Tenant Architecture

  • Database-Level Isolation: tenant_id column partitioning
  • API-Level Isolation: TenantFilter in request chain
  • JWT Claims: Tenant info embedded in access tokens
  • Tenant Selection: Login supports multi-tenant user assignment

3.3 Frontend Architecture

  • State Management: Zustand (lightweight alternatives to Redux)

  • Notifications: React Hot Toast for user feedback

3.4 Backend Architecture

  • Framework: Spring Boot 3.3.2 (Latest stable)

  • API Documentation: OpenAPI/Swagger (SpringDoc)

5.2 Authentication Flow

Frontend Authentication Implementation:

Session Lifecycle:
1. Login → JWT access token (memory) + refresh token (HttpOnly cookie)
2. API calls → Authorization: Bearer {token}
3. Token expiry → Auto-refresh via refresh endpoint
4. Refresh failure → Clear session and redirect to /login
5. Logout → Revoke refresh cookie server-side

5.3 Key Services

  • authService: Login, signup, MFA setup/verify, password reset
  • sessionService: Token refresh, session bootstrap, logout
  • storageService: Local storage management (legacy cleanup)
  • authAxios: Bare axios instance for session endpoints (no interceptors)

5.4 State Management (Zustand)

  • auth.store: User info, tokens, MFA status, session management
  • UI state: Modals, notifications, theme preferences
  • Lightweight approach: No boilerplate, direct mutation

5.5 Routing Architecture

Protected Routes Implementation:

  • Role-based route guards (superAdmin, tenantAdmin, employee, etc.)
  • RoleRedirect component maps authenticated users to their dashboard
  • Layout components (Sidebar, Header) with permission-aware navigation
  • Lazy loading of route components for code splitting

8. Security Assessment

8.1 Strengths ✓

✓ Strong Authentication
  • JWT with JJWT 0.12.5 (up-to-date library)
  • Short-lived access tokens (15 minutes)
  • Rotating refresh tokens (7-day expiry)
  • HttpOnly, Secure cookies for refresh tokens
  • MFA mandatory for privileged roles (SUPER_ADMIN, TENANT_ADMIN)
✓ Defense in Depth
  • CORS properly configured with allowed origins
  • CSRF protection via SameSite + X-Requested-With header
  • CSP headers (Content-Security-Policy, frame-ancestors 'none')
  • HSTS enabled with subdomain inclusion
  • Stateless session management (no server-side session storage)
✓ Account Security
  • BCrypt password hashing (cost 10, random salt per hash)
  • Account lockout after 5 failed attempts (15-minute window)
  • Password history tracking (5 previous passwords)
  • Have I Been Pwned integration (k-anonymity check)
  • Password reset tokens with 30-minute TTL
✓ Rate Limiting
  • AuthRateLimitFilter on login endpoints
  • Prevents brute force attacks
✓ MFA Support
  • TOTP (Time-based One-Time Password) implementation
  • QR code generation for authenticator apps
  • Recovery codes for account recovery
  • AES-256-GCM encryption for TOTP secrets
✓ Multi-Tenancy Isolation
  • Tenant context enforced at multiple layers (DB, API, JWT)
  • Row-level security via tenant_id filtering
  • Prevents cross-tenant data leakage

8.2 Security Configurations

Setting Value Security Impact
Access Token TTL 900,000 ms (15 min) Limits token compromise window
Refresh Token TTL 604,800,000 ms (7 days) Reasonable balance between UX and security
Lockout Duration 15 minutes Brute force mitigation
Password History 5 iterations Prevents immediate password reuse
MFA Enforcement Privileged roles only Recommended minimum (should be all users)
CSRF Protection SameSite + X-Requested-With Dual-layer CSRF mitigation
HSTS MaxAge 31,536,000 seconds (1 year) Forces HTTPS after first visit

8.3 Known Security Considerations

⚠️ MFA Enforcement Scope

Currently, MFA is enforced only for SUPER_ADMIN and TENANT_ADMIN roles. Consider expanding to all users for defense in depth.

⚠️ Flyway Migrations Disabled

Database migrations are currently disabled (spring.flyway.enabled=false). This should be re-enabled for schema versioning and production deployment.

⚠️ Swagger in Development

Ensure Swagger is disabled in production (SWAGGER_ENABLED=false must be set in environment).

10. API Integration Points

10.1 API Base Configuration

  • Base URL: http://localhost:8082/api/v1 (development)
  • Response Format: JSON with standard envelope: { success, message, data }
  • Error Format: RFC 7807 ProblemDetail: { detail, code, ... }
  • Authentication: Bearer token in Authorization header
  • Tenant Context: X-Tenant-ID or X-Tenant-Code headers

10.2 Frontend-Backend Communication

Frontend Axios Interceptor:
• Request: Adds Authorization: Bearer {token}
• Response: Unwraps { success, message, data }
• Error: Checks for 401 → triggers refresh
• Refresh: Uses authAxios (no interceptor loop)
• Session expired: Clears auth and redirects to login

11. Findings and Issues

11.1 Issues Discovered

Critical Issues

CRITICAL
🔴 Flyway Database Migrations Disabled

Issue: Database migrations are disabled in application.properties: spring.flyway.enabled=false
Impact: Prevents automated database schema versioning, makes deployment risky, no audit trail of schema changes
Location: ERP_Backend/src/main/resources/application.properties line 27
Recommendation: Enable Flyway migrations and implement versioned migration files in src/main/resources/db/migration/

CRITICAL
🔴 useAuth Hook Incomplete

Issue: The useAuth hook has a TODO comment and doesn't hydrate auth state from storage
Impact: Auth state is not restored from local storage on page load, causing loss of session
Location: SmartERP-AI-Frontend/src/core/hooks/useAuth.js line 8
File: This hook appears unused; session management is handled by sessionService.bootstrapSession()
Recommendation: Either complete the hook or remove it if redundant

High Priority Issues

HIGH
🟠 Mock Data in Production

Issue: Frontend has mock data files for all modules in src/data/*.mock.js
Impact: If mock data is used instead of API calls, frontend displays fake data
Location: SmartERP-AI-Frontend/src/data/
Recommendation: Verify all components use API calls, not mock data. Remove mock files in production build.

HIGH
🟠 Missing API Service Layer

Issue: Backend has controllers for all modules, but no corresponding API services found in frontend for most modules
Impact: Components may not have proper API integration to backend
Location: SmartERP-AI-Frontend/src/core/services/ - only has auth and session
Recommendation: Create service files for each major module (hrService, financeService, inventoryService, etc.)

HIGH
🟠 Database Schema Not Defined

Issue: While entities are defined in Java, there are no database migration files visible
Impact: Database initialization process unclear, schema versioning missing
Location: ERP_Backend/src/main/resources/db/migration/ (should exist)
Recommendation: Create Flyway migration files for all database schemas and enable Flyway

Medium Priority Issues

MEDIUM
🟡 Password Policy Endpoint Not Authenticated

Issue: GET /auth/password-policy is public but only relevant authenticated users
Impact: Minor, but could expose password policy before login
Location: SecurityConfig.java line 73
Recommendation: Consider if this endpoint should be authenticated or if public access is intentional

MEDIUM
🟡 Swagger UI Conditional but No Warning

Issue: Swagger is disabled by default but enabled via SWAGGER_ENABLED env var
Impact: Easy to accidentally expose API docs in production
Location: application.properties line 77-78
Recommendation: Add startup warning if Swagger is enabled in production

MEDIUM
🟡 No Request Logging

Issue: No visible request/response logging configured
Impact: Difficult to debug API issues, no audit trail of sensitive operations
Recommendation: Implement request logging with sensitive data masking

MEDIUM
🟡 Missing Error Boundary Components

Issue: No Error Boundary components visible in frontend
Impact: Single component error crashes entire app
Recommendation: Implement Error Boundary at application root and major sections

Low Priority Issues

LOW
🔵 Development Logs in Properties

Issue: PASSWORD_RESET_LOG_LINKS defaults to false but comment suggests development use
Impact: Minor, but should be clearly documented as dev-only
Recommendation: Ensure this is never enabled in production configuration

LOW
🔵 Vite Development Server Configuration

Issue: No explicit vite.config.js visible in project structure
Impact: Build configuration uses defaults
Recommendation: Create explicit vite.config.js for environment-specific configurations
